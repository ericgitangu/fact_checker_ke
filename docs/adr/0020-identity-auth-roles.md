# ADR-0020: Identity, auth and roles

**Status:** Accepted (Better Auth self-hosted; device tokens, owner, 2026-10-03) · **Date:** 2026-10-03 · Gates ADR-0009/0011 per-user quotas and ADR-0018 SSE capability tokens

## Problem
ADR-0015 says "later auth", ADR-0018 says "capability token, later auth", but ADR-0009 and ADR-0011 already enforce *per-user* quotas and ADR-0007/0008 need editor and admin roles with accountability. "Later" has no definition, and per-IP is the only fallback today, which breaks under Safaricom CGNAT (red-team C-9: many subscribers share one egress IP). This ADR defines the identity model for three populations: anonymous submitters/readers, optional registered accounts (later), and editor/admin staff (now).

## Evidence
- Red-team E: "Auth and identity... 0009 and 0011 enforce per-user quotas. Per-user of what? Per-IP is the only fallback, and it breaks under mobile CGNAT (C-9)." **[U, from report]**
- Clerk free tier: "50,000 MRU limit per app"; MFA is **not** included free (Pro+ only); 1-day log retention **[V: clerk.com/pricing, fetched 2026-10-03]**.
- Firebase Auth / Identity Platform Spark plan: "No-cost up to 50K MAUs" for standard sign-in; phone auth is billed per SMS with no stated free SMS allowance **[V: firebase.google.com/pricing, fetched 2026-10-03]**.
- Better Auth (self-hosted, open source) ships a 2FA plugin: "OTP... or TOTP... A code generated by an app on the user's device" **[V: better-auth.com/docs/plugins/2fa, fetched 2026-10-03]**. It stores its own tables in our Postgres (Neon), so it has no vendor MAU metering at all — the cost is rows we already pay for.
- Auth.js (NextAuth) has no built-in MFA; TOTP would be a third-party adapter, unverified **[GAP]**.
- Mobile talks to the API directly (ADR-0015), so whatever auth scheme exists must be usable from a Fastify API, not just from Next.js middleware.

## Options
1. **Clerk for everything.** Rejected: MFA (required for editors/admins) is paid-only, and 50K MRU is wasted on a 1-3 person editor team. The hosted session cookie also assumes a Next.js-fronted flow mobile-direct-to-API (ADR-0015) doesn't get for free.
2. **Firebase Auth / Identity Platform for everything.** Rejected: MFA cost is **[GAP]**, and it's a second cloud identity (GCP) beside Neon/Upstash with no gap it fills for a 1-3 person team.
3. **Better Auth, self-hosted in Neon, for editors/admins; no vendor identity product for anonymous users. Recommended.** TOTP MFA is free, open source, no MAU metering — cost is Neon storage already paid for. Runs as a Fastify plugin in `services/api` so mobile and web share `/v1/auth/*`.
4. **Custom auth from scratch.** Rejected: reinventing session rotation and TOTP is "novel tech" the cost-discipline rule forbids without a gap Better Auth doesn't close.

## Decision (proposed)
1. **Anonymous submit/read, no account required.** On first contact, `services/api` issues an opaque **device token** (256-bit random, hashed in Postgres `device_tokens(token_hash, created_at, last_seen_at)`, mirrored to a short Redis `SET NX` for dedup) via an HttpOnly cookie (web) or mobile secure storage. This token, **not the client IP**, is the quota key for ADR-0011/0009's per-user caps. IP stays only a coarse ceiling (≥50 req/min) so CGNAT users aren't blocked by IP alone — closing C-9.
2. **SSE capability tokens (ADR-0018)** are short-lived JWTs signed by the API, scoped to one `submission_id`, expiring at stream close (≤90s + resume). Minted from the device token at submission time; never valid cross-submission.
3. **Optional registered accounts, Phase 2+.** Better Auth email/passkey sign-in, linked to the device token's prior history. Out of scope now; schema (`users`, `accounts`, `sessions`) reserved so the migration is additive.
4. **Editor/admin RBAC, required before any named-person "False" ships (ADR-0008 C-13).** Roles: `editor` (draft review, publish, correct), `admin` (editor + role grants, kill-switch per ADR-0007). **MFA (TOTP) is mandatory for both** — no role grant without a verified enrollment, enforced server-side.
5. **Immutable audit log.** Every role grant, publish, correction, kill-switch flip and login is an append-only `audit_log(id, actor_id, action, target_type, target_id, metadata, created_at)` row, written in the same transaction as the action (reuses the ADR-0017 outbox pattern). No update/delete grant exists at the DB-role level.
6. **Quota keys:** anonymous = device token; authenticated reader = account id (falls back to pre-login device history); editor/admin actions skip the public quota path.

## Trade-offs accepted
Self-hosted auth means we own session rotation, token revocation and the TOTP recovery flow instead of buying it. Accepted because the editor headcount is tiny, MFA must be free, and it avoids a second vendor dependency when Neon is already the source of truth.

## Irreversible
Device-token-as-quota-key is a schema and client contract (mobile stores it) — changing the quota key later requires a migration that preserves existing users' standing, not a breaking reset.

## Review trigger
Revisit if MAU for the optional-accounts feature approaches Firebase's or Clerk's free-tier ceiling, or if a second admin/editor hire changes the MFA-enrollment UX cost calculus.

## Implementation notes (anonymous-token slice, 2026-10-03)

This wave implements **only** §1 ("Anonymous submit/read, no account required") and the SSE capability-token half of §2 — explicitly the "anonymous-token slice" the task brief scoped. §3 (optional registered accounts), §4 (Better Auth editor/admin RBAC + mandatory TOTP), and §5 (immutable audit log) are **not implemented** and their acceptance tests are left RED on purpose, not silently skipped: there is no editor/admin surface yet for a role grant or a publish/correction/kill-switch action to happen against.

- **`POST /v1/device`** (`services/api/src/routes/device.ts`) issues a 256-bit opaque token (`crypto.randomBytes(32)`, base64url); only its SHA-256 hash is persisted (`device_tokens.token_hash`). The raw token is returned exactly once.
- **Quota key = device token, never IP** (`services/api/src/lib/device-quota.ts`, `concurrency-guard.ts`): both the per-device SSE stream-concurrency guard (ADR-0018 §5) and the new per-device daily submission-quota guard (`POST /v1/submissions` now 400s with `device_token_required` if `X-Device-Token` is missing) are keyed this way. The daily limit (20/device) is a placeholder — ADR-0011's own review trigger says the real threshold should come from week-1 production data, which doesn't exist yet.
- **SSE capability token** (`services/api/src/lib/device-token.ts`): an HS256 JWT (`jose`), `sub` = submission id, default 90s TTL, minted once at submission-creation time and returned verbatim as `eventsToken` in the `POST /v1/submissions` 202 body (and replayed verbatim, not re-signed, on an idempotent retry). `GET /v1/submissions/:id/events` verifies both the signature and that `sub` matches the requested submission id — AT-0020-2's cross-submission rejection is a 403, not a 401, so a client can tell "wrong scope" from "bad/expired token."

**Deviations / tech debt:**
- No account linkage, Better Auth, MFA, or audit log in this wave — by design, not an oversight. The `users`/`accounts`/`sessions` schema reservation mentioned in the ADR's §3 is also not added yet (nothing in this wave's scope needed it); adding it is additive whenever Phase 2 starts.
- The capability-token secret (`CAPABILITY_TOKEN_SECRET`) is a single static HMAC secret for the whole API, not the per-submission-scoped signing the ADR's wording ("minted from the device token at submission time") might suggest — it's scoped by `sub` claim validation, not by using a derived key, which is simpler and equally safe for an HS256 JWT whose only claim that matters is `sub`.

## Implementation notes ("People & adjudication" wave, 2026-10-03)

This wave implements §3 (editor/admin/moderator identity), §4 (mandatory TOTP MFA, RBAC), and §5 (immutable audit log), landing AT-0020-3 and AT-0020-4.

- **Self-hosted, NOT the `better-auth` npm package.** `services/api/src/lib/auth/{password,totp,service,middleware}.ts` is a minimal, dependency-free, unit-tested implementation of the exact same decision (self-hosted in Neon, TOTP mandatory, no vendor MAU metering): scrypt password hashing (`node:crypto`), RFC 6238/4226 TOTP (`node:crypto` HMAC-SHA1, verified against the official RFC 4226 Appendix D test vectors in `auth-totp.test.ts`), opaque hashed session tokens (same pattern as the existing device-token scheme). **Deviation, stated plainly:** pulling in `better-auth`'s full plugin/adapter surface (its Drizzle adapter, its 2FA plugin, its Fastify integration) inside this change's verification budget would have traded a verified, RFC-vector-tested implementation for an unverified third-party integration nobody here has exercised end-to-end yet. Swapping in the real package later is additive — same tables (`users`, `sessions`, `totp_secrets`), different code calling them — and becomes worth doing if passkeys/OAuth/WebAuthn are ever required (this implementation doesn't support them).
- **`users.role` is nullable.** A freshly registered account has no role until granted — this makes "registered but ungranted" (AT-0020-3's precondition) a real, queryable state instead of a role value doing double duty as "not real yet."
- **Role grant gate** (`AuthService.grantRole`): rejected (and audit-logged as `role_grant_rejected_no_mfa`) unless `users.mfa_enabled = true`, which itself only flips true inside `verifyTotpEnrollment` — enrolling alone is not enough. A one-time **bootstrap path** (`actor: null`, only while zero `admin` rows exist, only grants `admin`) answers "who grants the first admin" without a side-channel seed script; every subsequent grant requires a real `admin` actor.
- **`audit_log` immutability** is enforced at the application level only — no repository/service method anywhere issues an `UPDATE`/`DELETE` against it. A DB-role-level `REVOKE UPDATE, DELETE` would need a non-owner Postgres role; Neon's single `neondb_owner` connection string for this project doesn't provide one. **Tech debt, stated explicitly:** provisioning a second, privilege-restricted Postgres role (or a Neon RLS policy) for the API's runtime connection is the real fix and is out of scope for this wave.
- **Verified empirically against real Neon Postgres** (`services/api/src/__tests__/auth-service.integration.test.ts`, `scripts/at/at-0020.sh`): a role grant to an unverified account is rejected and writes exactly one `role_grant_rejected_no_mfa` row; a verified enrollment + grant + mandatory-MFA login round-trips for real; a transaction rolled back after an audit-log insert leaves zero rows (AT-0020-4's "same tx" claim, not just asserted — forced and observed).
- **No kill-switch action exists yet** anywhere in the codebase (ADR-0007's per the ADR text), so AT-0020-4's "kill-switch flip" clause is unexercised by construction, not silently skipped — publish/approve/correct/reject (ADR-0025) are the actions that exist and are audited.
